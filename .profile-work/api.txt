Complete Provider Registration and Service Approval API Flow API updates checked against the local backend and project documentation: 15 October 2026. Server: https://jobhub.pentarixlabs.com; endpoint paths below include /api/v1. Base URL: /api/v1 After authentication, send: Authorization: Bearer <accessToken> Content-Type: application/json The complete workflow is: Register → Verify email/phone → Create provider profile and select market → Select service type → Load dynamic onboarding schema → Select service options → Add languages → Configure availability → Configure service locations → Select skills → Upload shared documents → Add certificates/education → Submit dynamic requirements → Check completion → Admin reviews pending items → Provider service becomes APPROVED 1. Register the provider There are two supported registration methods. Option A: Email/password POST /api/v1/auth/register Request: { "email": "provider@example.com", "password": "StrongPassword123!", "accountType": "SERVICE_PROVIDER" } Password must contain 10–72 characters. Response: 201 Created { "id": 25, "username": "provider", "email": "provider@example.com", "phoneNumber": null, "status": "PENDING", "emailVerified": false, "phoneVerified": false, "roles": ["SERVICE_PROVIDER"] } Verify email POST /api/v1/auth/email/verify { "email": "provider@example.com", "otp": "123456" } Response: { "accessToken": "<jwt>", "refreshToken": "<refresh-token>", "tokenType": "Bearer", "expiresIn": 900, "user": { "id": 25, "username": "provider", "email": "provider@example.com", "status": "ACTIVE", "roles": ["SERVICE_PROVIDER"] } } Option B: Phone OTP Request an OTP: POST /api/v1/auth/otp/request { "phoneNumber": "+94764233731", "accountType": "SERVICE_PROVIDER" } Response: 202 Accepted { "message": "If the phone number is eligible, an OTP has been sent", "expiresIn": 300 } Verify: POST /api/v1/auth/otp/verify { "phoneNumber": "+94764233731", "otp": "123456", "accountType": "SERVICE_PROVIDER" } This creates the provider account if the phone number is new and returns the same token response used by email verification. 2. Provider Login Providers can sign in using email/password or phone OTP, depending on how the account was registered. Option A: Email/password login POST /api/v1/auth/login Content-Type: application/json Request: { "identifier": "provider@example.com", "password": "StrongPassword123!" } identifier accepts either the account email or generated username. Successful response: 200 OK { "accessToken": "<jwt-access-token>", "refreshToken": "<refresh-token>", "tokenType": "Bearer", "expiresIn": 900, "user": { "id": 25, "username": "provider", "email": "provider@example.com", "status": "ACTIVE", "roles": ["SERVICE_PROVIDER"] } } Possible errors: ● 400 Bad Request : invalid or missing fields. ● 401 Unauthorized : incorrect username/password or inactive account. ● Email/password login works only after email verification activates the account. Use the access token for protected requests: Authorization: Bearer <accessToken> Option B: Phone OTP login Phone-registered providers do not have a password by default. They sign in by requesting another OTP. Request login OTP POST /api/v1/auth/otp/request Content-Type: application/json { "phoneNumber": "+94764233731", "accountType": "SERVICE_PROVIDER" } Response: 202 Accepted { "message": "If the phone number is eligible, an OTP has been sent", "expiresIn": 300 } Verify login OTP POST /api/v1/auth/otp/verify Content-Type: application/json { "phoneNumber": "+94764233731", "otp": "123456", "accountType": "SERVICE_PROVIDER" } Response: 200 OK { "accessToken": "<jwt-access-token>", "refreshToken": "<refresh-token>", "tokenType": "Bearer", "expiresIn": 900, "user": { "id": 25, "username": "provider-25", "email": null, "status": "ACTIVE", "roles": ["SERVICE_PROVIDER"] } } For an existing phone number, this logs in the provider rather than creating another account. Refresh expired access token The access token normally expires after 900 seconds. Use the refresh token without asking the provider to log in again: POST /api/v1/auth/refresh Content-Type: application/json { "refreshToken": "<current-refresh-token>" } Response: { "accessToken": "<new-access-token>", "refreshToken": "<new-refresh-token>", "tokenType": "Bearer", "expiresIn": 900, "user": { "id": 25, "username": "provider", "email": "provider@example.com", "status": "ACTIVE", "roles": ["SERVICE_PROVIDER"] } } The refresh token is rotated. The app must replace both stored tokens with the new values. Logout current session POST /api/v1/auth/logout Content-Type: application/json { "refreshToken": "<refresh-token>" } Response: 204 No Content Logout from every device POST /api/v1/auth/logout-all Authorization: Bearer <accessToken> Response: 204 No Content Provider Onboarding 2. An empty optionIds array means a common service-wide field; [12, 13] applies one field to either option. Answer a fieldId only once even when several selected options use it. Frontend behavior: ● Always display commonFields . ● Display an option’s fields only when that option is selected. ● Use fieldType to choose the input control. ● Use options for select/multiselect values. ● Use condition to show or hide conditional fields. ● Show approval state for fields where requiresApproval is true. documents exist, are valid, and are approved when approval is required. ● Mandatory skills are selected and approved when required. ● A valid certificate exists when certificates are required. ● Education exists when education is required. ● Availability is configured when enabled. ● Required locations exist for selected physical-delivery options. ● The minimum number of approved service options is selected. ● All required dynamic provider fields are submitted and approved when required. There is no separate provider “submit application” endpoint. Approval state is recalculated automatically whenever the provider or administrator changes relevant information. Status meanings verificationStatus PENDING APPROVED REJECTED Assignment statuses ● providerStatus : provider-controlled ACTIVE or INACTIVE ● adminStatus : administrator-controlled ACTIVE or INACTIVE ● status / effectiveStatus : ACTIVE only when both are active A service can therefore be verified but still unavailable: { "verificationStatus": "APPROVED", "providerStatus": "INACTIVE", "adminStatus": "ACTIVE", "status": "INACTIVE" } Frontend polling recommendation After submitting or updating any requirement, refresh: GET /api/v1/providers/me/completion GET /api/v1/providers/me/service-types The app should consider the service ready only when: verificationStatus == APPROVED AND effectiveStatus == ACTIVE Admin configuration and review updates Super Admin service setup: POST /api/v1/admin/provider-types/setup PUT /api/v1/admin/provider-types/{providerTypeId}/setup Include gallery and responsibilities as required arrays, even when empty. Both endpoints accept icon, coverImage, gallery, and responsibilities. PUT replaces content: icon: null and coverImage: null remove those properties; gallery: [] and responsibilities: [] clear those collections. Media keys must be unique per service/option, and gallery and responsibility display orders must be unique. Supplying icon synchronizes legacy iconUrl to icon.url. Upload images before referencing them: POST /api/v1/uploads/images Content-Type: multipart/form-data; file: <image> Returns 201 with key, url, contentType, and size. Maximum 10 MB; JPG, PNG, WebP. Safe SVG is supported for Super Admin service assets; provider profile photos remain raster-only. Use url for profilePhoto; use the returned key and url for structured service media. Private files: POST /api/v1/uploads/documents accepts PDF, JPG, PNG, WebP up to 100 MB and returns 200 with key, url, contentType, and size. Store key in documentKey fields. GET /api/v1/uploads/view-url?key={URL-encoded-object-key} returns a viewing URL valid for 10 minutes. Providers can view their own files; authorized admins can view provider files. Create an option and dynamic fields together POST /api/v1/admin/provider-types/{providerTypeId}/options Example request: { "code": "HOME_CARE", "name": "Home Care", "description": "Care provided at the customer's home", "displayOrder": 1, "schedulingModel": "TIME_BASED", "locationEnabled": true, "deliveryModes": ["PROVIDER_TO_CUSTOMER"], "fulfillmentModel": "ONE_TO_ONE", "defaultCapacity": 1, "requiredProviderCount": 1, "bookingMode": "MANY_AT_A_TIME", "providerSelectionMode": "OPEN_REQUEST", "pricingOwner": "ADMIN", "allowedPaymentMethods": ["CASH", "CARD"], "icon": null, "coverImage": null, "gallery": [], "responsibilities": [], "dynamicFields": [ { "definition": { "scope": "PROVIDER_REQUIREMENT", "reuseScope": "ASSIGNMENT", "code": "CARE_EXPERIENCE", "label": "Care experience in years", "fieldType": "NUMBER", "required": true, "requiresApproval": false, "displayOrder": 1 } } ] } Omit fieldId to create a field. Omit optionId/optionIds inside a new definition to assign it to the newly created option. The response supplies optionId and generated fieldId values. PUT /api/v1/admin/provider-types/{providerTypeId}/options/{optionId} edits the option and fields in one transaction. Include fieldId and a full definition to update an existing field. Without option IDs, existing field assignments are preserved; explicit optionIds replaces assignments and must include the current option, or [] for a common field. Editing shared fields affects all options using them. Omitted, null, or empty dynamicFields preserves existing fields; use the field status API to deactivate one. Option PUT also requires gallery and responsibilities and replaces media/responsibility content.
